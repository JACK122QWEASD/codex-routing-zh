# Codex 分层调度协议

**让 Codex 把简单活派给便宜模型，难活自己干。**

一套跑在 ChatGPT 桌面端 / Codex CLI 里的调度规则：接到任务后先拆分、按 9 维量表定级、
按难度分派给不同成本的模型，能并行的并行跑，失败按预案兜底。

不需要改代码、不需要插件——只是几份 Markdown 规则文件 + 两个小工具脚本。

[English](./README.md)

---

## 为什么需要它

复杂任务拆开看，往往混着大量极简单的子步骤。全部丢给强模型，又慢又贵。

实测一轮真实任务：**12 个子任务里 10 个是机械活**，它们占的时间不到 5%，
却因为混在流程里被强模型顺手做了——而强模型一轮推理要 6 秒。

## 实测数据（这是本项目的立身之本）

### 弱模型 vs 强模型写代码 —— 9 道题正面对撞

生成的代码直接挂断言用 node 跑，**跑过才算对**：

| 任务 | 弱档 GLM（关思考） | 强档 v4-pro |
|---|---|---|
| 回文判断 | ✅ 3.6s / 128tk | ✅ 9.7s / 799tk |
| 防抖函数 | ✅ 3.2s / 113tk | ✅ 6.0s / 523tk |
| 二分查找 | ✅ 3.7s / 153tk | ✅ 12.1s / 989tk |
| 深拷贝 | ✅ 4.0s / 168tk | ✅ 42.6s / 2791tk |
| LRU 缓存 | ✅ 4s / 191tk | ✅ 28s / 1979tk |
| 限流器（异步） | ✅ 8s / 344tk | **❌ 47s / 3356tk** |
| 状态机 | **❌ 7s / 299tk** | ✅ 34s / 2262tk |
| 既有风格（D9=3） | ✅ 3s / 283tk | ✅ 4s / 593tk |
| 跨模块接口（D2=3） | ✅ 6s / 400tk | ✅ 26s / 2042tk |
| **合计** | **8/9，86s，1979tk** | **8/9，229s，15434tk** |

**正确率打平，弱档快 2.7 倍、省 87%。**

### 其他关键实测

| 优化项 | 效果 |
|---|---|
| 弱模型关闭"思考" | 单任务 242tk → **28tk**（省 88%），输出不变 |
| 入口/正文分离 | 每轮 token 15,501 → **8,812**（省 43%） |
| 批量派发（vs 逐个） | 强档决策轮次 N → **2** |
| 并发度 | 弱档 5/8/12 耗时 5.64/4.93/4.97s，**12 都不掉速** |
| Prompt 缓存 | 命中率 **94.5%**（1280/1354） |

### 三个反直觉的结论

1. **"写代码"不是升档理由** —— 单函数实现，弱档和强档正确率一样
2. **上下文能不能一次贴全，才是分水岭** —— 弱档怕的不是"理解上下文"，是"自己去找上下文"
3. **强档也不是免检的** —— 它在限流器上花 47 秒还写错了。任何档位的产出都要跑测试

## 环境要求

| 项 | 要求 |
|---|---|
| Codex | 桌面端或 CLI（**0.122+**，此版本起只支持 Responses 协议） |
| 系统 | 脚本用了 `grep` / `sed` / `chmod`，需 Unix 环境（macOS / Linux）。Windows 请走 WSL |
| Python | 3.7+（只用于拼 JSON，**不依赖 tomllib**） |
| Node | 可选，用于 `node --check` / `node --test` 做校验 |
| 弱模型 | 任意提供 Chat Completions 的厂商（火山方舟 / DeepSeek / 智谱 / 百炼…都行） |

> 项目里的模型名、端点都是**示例值**，换成你自己的即可，规则本身与厂商无关。

## 快速开始

### 1. 安装

```bash
git clone https://github.com/JACK122QWEASD/codex-routing.git
cd codex-routing
./install.sh
```

`install.sh` 做两件事：
- 把全局入口写到 `~/.codex/AGENTS.md`（这样任何目录的 Codex 会话都会加载）
- 从模板生成 `.route-state.json` 和 `~/.codex/config.toml`

### 2. 配置模型

编辑 `~/.codex/config.toml`，填你自己的模型端点和密钥：

```toml
model = "deepseek-v4-pro"
model_provider = "deepseek"

[model_providers.deepseek]
name = "DeepSeek (强)"
base_url = "https://api.deepseek.com/v1"
env_key = "DEEPSEEK_API_KEY"
```

> **密钥不要写进本仓库。** 用 `env_key` 走环境变量，或写在 `~/.codex/config.toml`（权限 600，不进版本库）。

### 3. 用

重启 Codex（桌面端需 `Cmd+Q` 完全退出再打开），新开对话。

它会先问三个配置问题：

```
【开工配置 1/3】是否进入模型配合模式？
【开工配置 2/3】拆分颗粒度？
【开工配置 3/3】强档 / 弱档模型确认
```

然后给出任务分配方案，**等你说"执行"才动手**。

## 文件结构

```
agent.md            调度协议正文（按需加载，不占每轮上下文）
rubric.md           9 维难度量表 + 编码任务路由判据（定级时才读）
weak-channel.md     弱模型调用通道 + 批量派发脚本（派发时才读）
prompts.md          弱模型 Prompt 模板库（派发时才读）
tools/merge.py      合并落盘工具
tools/roundtrip.py  回译校验工具
examples/           配置模板（全局入口、config.toml、route-state）
install.sh          安装脚本
```

**设计要点**：只有一份几十行的入口文件每轮加载，其余全部**按需读取**——
这是实测省 43% token 的关键。

## 规则速览

### 定级

9 个维度（可验证性、上下文半径、推理深度、工具需求、决策自由度、失败代价、歧义度、输出规模、领域依赖）
各打 0–4 分，加权算出**难度分 0–100**，映射到 L1–L5，再过 7 道硬门槛。

### 路由

| 档 | 承接 | 说明 |
|---|---|---|
| S 强 | L4/L5 | 主会话模型 |
| M 中 | L3 | 编码任务可下放弱档（见 rubric §六） |
| W 弱 | L1/L2 | 便宜模型，直连 HTTP 不走 Codex |

### 执行清单（逐项打勾，缺一项即违规）

```
派发前  □ 用 prompts.md 模板（不临场现写）
        □ canary 探测（不通就升档）
        □ 脚本自包含
执行中  □ 一次并行跑完 + wait
        □ 脚本化校验（看退出码）
        □ 回译校验（可逆任务，零 token）
        □ merge.py 合并
        □ 抽检 N 条
收尾    □ 收尾报告
```

### 兜底

重试 1 次 → 降为串行重试 → 升档 → 强档接手。整组 ≥50% 失败判定厂商故障。
**任何兜底都必须写进收尾报告**，不许静默降级。

## 换成你自己的模型

改 `.route-state.json` 一处即可：

```json
{
  "strong_model": "deepseek-v4-pro",
  "cheap_model": "glm-5-2-260617",
  "cheap_no_think": true
}
```

注意事项：
- **强档必须支持 Responses 协议**（Codex 0.122+ 只认它）
- **弱档走直连 HTTP**，只需 Chat Completions——所以火山方舟、智谱这类都能用
- 弱档如果是推理模型，**必须关思考**（`cheap_no_think: true`），否则 88% 的 token 烧在推理上

## 常见问题

**Q：为什么桌面端报错"Missing environment variable"?**
A：从 Dock 启动的 App 读不到 shell 环境变量。两种解法：把密钥写进 `~/.codex/config.toml` 的
`experimental_bearer_token`（权限 600），或在终端执行 `launchctl setenv KEY value` 后重启。

**Q：规则没生效，它直接开干了？**
A：检查全局入口是否就位：`ls -l ~/.codex/AGENTS.md`。Codex 的指令层级是
全局 → 仓库根 → 子目录，桌面端对话若不在项目目录，只有全局层生效。

**Q：能用在 Codex CLI 上吗？**
A：能，但 CLI 是非交互的，走的是"声明配置 + 出方案 + 执行"流程（见 agent §0.5）。
